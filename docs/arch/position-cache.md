# Shared position cache

_GrandForge reference. Load this file only when working in this area; see [CLAUDE.md](../../CLAUDE.md) for the routing table._

`POST /api/positions/cache` accepts writes from **anonymous** visitors (`optionalAuth`, `contribute` tier). It has to: sign-up is optional by design, so the old `requireAuth` meant almost nobody wrote, the cache never filled, and every reader got a permanent miss. In exchange the server validates the payload itself instead of leaning on the auth gate. All the decision logic is pure and unit-tested in **`backend/positionCacheGuards.ts`** (65 tests); `routes/positions/cache.ts` applies decisions, it does not make them. Guard numbering follows `docs/superpowers/audits/backend-audit.md` §3.

- **Poisoning is the threat, not storage.** A wrong eval is silent, cross-user, and scores a good move as a blunder in somebody else's finished review. Storage is bounded by the pre-existing 60-day `computedAt` TTL/LRU.
- **Trust-on-second-confirmation.** A row carries `confirmations` (default `1` — a row counts as its own first submission) and `contributors`. `GET /positions/eval` filters on `confirmations: {$gte: TRUST_THRESHOLD}`, so **an entry is served only once two *independent* submissions agree on it**. Consequence to expect, not to debug: a freshly deployed cache serves nothing until positions are seen twice, so the hit rate starts at zero and climbs. Misses are free (the review falls through to local WASM), so it reads as "no speedup yet". `TRUST_THRESHOLD` is one constant if that trade needs relaxing.
- **The challenger slot** is what makes disagreement safe. A deeper search legitimately disagrees sometimes (depth 14 says +0.2, depth 30 says +2.5) so a disagreeing write can't just be refused — but `depth` is client-supplied and unverifiable, so if a deeper claim could overwrite a *trusted* row then erasing the whole cache would cost one POST per position. Instead a dissenting write parks in `challenger` and only takes over once independently confirmed in its own right. **Agreement is checked before depth everywhere**: a matching second opinion outranks a lone claim to have searched further. The `CacheDecision` action names say exactly whose data lands where — `supersede-primary` (incoming wins, old primary demoted to challenger so the dissent survives) is a different thing from `promote-challenger`, and conflating them was a real bug during development.
- **One contributor can't confirm their own entry twice** — otherwise poisoning costs one POST plus a retry. `contributorKey` is `u:<userId>` for a logged-in user and `a:<16-char HMAC>` of the IP otherwise, salted with `IP_HASH_SALT ?? JWT_SECRET` (no new env var required). With **no** secret it returns `null` rather than an unsalted hash, because an unsalted IP hash is brute-forceable across all of IPv4 — that would turn an abuse control into a PII store. A `null` key still records the write; it just can't be deduped.
- **`linesRejection` replays every move of every PV** through chess.js, not just the first: the PV tail is displayed as "best line", so a legal-head/garbage-tail payload still shows a reader nonsense. Bounded at 5 lines × 64 plies. It also pins `lines[0].eval === evaluation` (the honest client derives both from one search line) and contiguous `multipv` from 1.
- **A 4-field FEN is required, not normalized server-side.** A 6-field write would store a row every reader's query can never match — invisible rather than wrong. `turn` is derived from the FEN and the client's `turn` field is accepted-and-ignored.
- `positions/eval` projects explicitly (`fen engineVersion depth evaluation lines confirmations`): the salted `contributors` hashes and the deliberately-non-authoritative `challenger` must not reach a public response.
- Client side, `frontend/src/services/positionCache.ts` skips the request below `MIN_CACHE_DEPTH` (parity-tested against the backend constant, same pattern as `MAX_CACHED_PV`) and swallows every failure — a 429 from the write budget and a 400 from a guard are both correct outcomes, not errors a user should see.
- **Provenance is surfaced, quietly.** `MoveReview.evalSource` (`'cache' | 'tablebase' | 'engine'`, and declared in `moveReviewSchema` or it's stripped on save) feeds `summarizeEvalSources` in `reviewUtils.ts` → the `.eval-source-row` line in `ReviewSummaryCard`. It's hidden when nothing was reused, and an absent `evalSource` counts as `unknown`, never as `engine` — an old saved review must not claim it did all its own work.
