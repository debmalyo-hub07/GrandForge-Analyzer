# API, deployment and server build

_GrandForge reference. Load this file only when working in this area; see [CLAUDE.md](../../CLAUDE.md) for the routing table._

Route modules live under `backend/routes/**`, each exporting a default Express app built by `createApp(tier?)` (CORS allowlist + 5 MB JSON + a tiered rate limit). Rate limiting is deliberately **per route module** (~25 buckets/IP) because one game review legitimately fires ~1 positions request per ply, which would blow a single global bucket; the tiers in `backend/createApp.ts` are `review` 900 (positions eval/tablebase) · `browse` 400 (openings lookup/tree, master games, explorer lookup) · `contribute` 300 (anonymous position-cache **writes** — its own bucket so a write flood can never 429 the reads a review depends on) · `default` 150 · `strict` 20 (login/register, the chess.com/lichess import routes, admin migrate). `backend/createApp.test.ts` pins each route to its tier and asserts the review budget exceeds the 600-ply `moveReviews` bound. Shared-store limiting is Phase 6. They are **all mounted behind one regex dispatch table in `backend/router.ts`**, which has **two deployment entry points**: (1) the *single* Vercel Serverless Function `api/[...path].ts` — a 1-file adapter that only re-exports `backend/router`; it must stay at repo-root `api/` (Vercel's functions convention) and Vercel Hobby allows at most **12 functions**, so ~25 one-file-per-function routes would fail to deploy (`vercel.json` sets `includeFiles: "backend/**"` for the bundle; `backend/` itself is outside `api/`, so Vercel never functionizes route modules) — and (2) `backend/index.ts`, the persistent server Render runs (`render.yaml` blueprint; also `npm run dev` locally — listens on `PORT ?? API_PORT ?? 3000`, graceful SIGTERM drain, 120 s keepAliveTimeout for Render's proxy). Dev, Render, and Vercel all run one identical routing table — **to add a route, drop it under `backend/routes/**` and register one line in `backend/router.ts`** (each inner app registers its full `/api/...` path).

- **Dual-deploy client contract**: `.env.production` (committed, public values only) sets `VITE_API_BASE_URL` to the Render base; `frontend/src/services/apiBase.ts` resolves primary/fallback, probes `{primary}/health` at boot (4 s timeout — doubles as the Render warm-up ping), and `apiClient.ts` interceptors fail over stickily to same-origin `/api` on network/502/503/504 errors with a 5-min recovery re-probe. Unset `VITE_API_BASE_URL` (dev, Playwright) short-circuits all of it to `/api`. Renaming the Render service must update `render.yaml` + `.env.production` + the vercel.json CSP together (see `docs/deploy-render.md`).
- CORS: `backend/corsOrigins.ts` builds the allowlist — `FRONTEND_URL`, CSV `CORS_EXTRA_ORIGINS`, plus localhost 5173/4173 always (unit-tested; vitest include covers `backend/**/*.test.ts`).
- DB connection: `backend/db.ts` — `connectDB()` caches the mongoose connection and shares one in-flight connect promise (concurrent handlers at game load would otherwise race a half-open socket since `bufferCommands: false`). It loads `.env` manually (`loadLocalEnv`); `dbName` is always `chess-analyzer`. Pool is environment-keyed on `process.env.VERCEL`: serverless `maxPoolSize 2` / socket 10 s / idle 15 s, persistent `maxPoolSize 20` / socket 45 s / idle 60 s. The serverless pool is small on purpose — Atlas M0 caps at 500 connections total and dozens of lambdas can be warm during one review, so a bigger per-lambda pool only reserves slots it never uses.
- **Health endpoints are two different things.** `/api/health` is DB-free and is what Render health-checks, the keep-alive pinger hits, and `apiBase.ts` probes for failover — it must stay cheap so an Atlas blip can neither restart the service nor stampede every browser into failover. `/api/health/deep` does a real `admin().ping()`, returns 503 when the DB is unreachable, and reports `runtime` plus `proxy.hops`/`clientIp` — that last part exists to verify `trust proxy` against a real deploy (both `createApp()` and the outer `router.ts` app set it to 1; if the platform ever adds a hop, every request rate-limit-keys to the same intermediate IP). Checklist in `docs/deploy-render.md`.
- **Server build**: Render runs compiled CommonJS (`npm run api:build` → `tsconfig.server.json` → `dist-server/`, plus a `{"type":"commonjs"}` marker written by `scripts/buildServer.mjs` to override the root `"type": "module"`), not `tsx`. Free-tier Render spins down after 15 min idle so cold start is the normal path, and tsx re-transpiled the whole backend on each one. Consequence for `package.json`: **`dependencies` means "the API imports this at runtime"** — the entire frontend tree (react, the stockfish package, vite, playwright, the vercel CLI) is devDependencies so `npm prune --omit=dev` strips it from the slug; `vercel.json` pins `installCommand: npm ci --include=dev` so the frontend build still gets them. The server build uses `lib: ES2022` + `types: node` (no DOM), so `fetch`/`Response.json()` resolve to `unknown` there and need an explicit cast that the root tsconfig would not demand.
- `POST /api/engine-index/migrate` pages with `?limit=N` (default 500, max 5000) and returns `remaining` — the serverless 30 s ceiling no longer bounds it on Render. `ReviewJob` rows TTL-expire 30 days after `updatedAt` (results live on Game/Session, unaffected).
- Auth: `backend/auth.ts` — JWT bearer tokens, 7-day expiry. `requireAuth` (401 if absent) vs `optionalAuth` (attaches user if present, never blocks). Most analysis/import endpoints are intentionally public.
- Models in `backend/models/`, Zod request schemas in `backend/zodSchemas.ts`. Cached evals are stored **White-relative** (Position model convention) — the review service flips to/from mover-relative at the boundary. `ENGINE_VERSION_VALUES` in `zodSchemas.ts` is the single source of truth for every server-side engine enum (position cache read/write, user preferences, the `User` model) — inlining the list again is what let `sf18-full` shard the cache into a namespace nobody reads while `sf18-lite-mt` users could neither read nor write it; a source-level test in `zodSchemas.test.ts` enforces it. `Game`'s dedupe index uses `partialFilterExpression: { 'metadata.sourceGameId': { $type: 'string' } }`, not a plain sparse compound index — the old form collided on the second hand-played/PGN upload (E11000). Dropping the stale `metadata_1_metadata.sourceGameId_1_userId_1` index is a one-time Atlas step; runbook in `docs/deploy-render.md`.
